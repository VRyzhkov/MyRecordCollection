# MyRecordCollection — конспект проекта

Обновлено: 31 августа 2026 года.

## Цель

Нативное Android-приложение, которое показывает музыкальную коллекцию пользователя Яндекс Музыки в виде анимированной карусели альбомов.

## Согласованные требования

1. При запуске приложение проверяет наличие access token или refresh token для доступа к данным Яндекс Музыки.
2. В приложении один основной экран.
3. После успешной авторизации загружается коллекция пользователя.
4. Избранные музыкальные элементы преобразуются в уникальные альбомы и группируются по исполнителю или группе.
5. Альбомы представлены круглыми элементами карусели.
6. В альбомной ориентации траектория начинается снизу слева, проходит через центр и заканчивается снизу справа.
7. В портретной ориентации траектория начинается сверху справа, проходит через центр и заканчивается снизу справа.
8. При приближении к центру элемент плавно увеличивается, после прохождения центра — уменьшается.

## Важное ограничение API

Публичная официальная документация API Яндекс Музыки для получения библиотеки пользователя не обнаружена. Официальный Яндекс OAuth существует, но конкретный сервис должен официально предоставлять разрешения и документировать свои маршруты.

Популярная библиотека `MarshalX/yandex-music-api` прямо называет используемый API недокументированным и полученным методом reverse engineering. Она показывает наличие операций для избранных треков и альбомов, а также экспериментальный Device Flow с `access_token` и `refresh_token`. Эти возможности не являются стабильным официальным контрактом Яндекса и могут измениться или перестать работать.

Следствия:

- сетевую реализацию нельзя связывать напрямую с UI;
- сначала разрабатываем экран и карусель на локальных тестовых данных;
- доступ к Яндекс Музыке помещаем за интерфейсом репозитория;
- токены не встраиваем в исходный код и не публикуем в Git;
- перед распространением приложения отдельно проверяем условия использования Яндекс Музыки;
- поломка неофициального API не должна требовать переписывания интерфейса и бизнес-логики.

## Модель состояния единственного экрана

```text
CheckingAuth → SignedOut
             ↘ Loading → Content
                       ↘ Empty
                       ↘ Error
```

- `CheckingAuth` — проверка сохранённых токенов;
- `SignedOut` — требуется вход через сайт Яндекса;
- `Loading` — загрузка коллекции;
- `Content` — сгруппированные альбомы;
- `Empty` — в избранном нет подходящих альбомов;
- `Error` — ошибка авторизации, сети или формата неофициального API.

## Карусель

Карусель лучше реализовать как собственный Compose-компонент на `Canvas` или слое с вычисляемыми координатами, а не как стандартный горизонтальный список.

Для каждого элемента используется нормализованная позиция `t` от `0` до `1`:

- траектория задаётся квадратичной кривой Безье;
- ориентация экрана выбирает набор контрольных точек;
- масштаб максимален при `t = 0.5`;
- порядок отрисовки зависит от масштаба, чтобы центральный альбом находился сверху;
- прокрутка изменяет общую позицию карусели;
- после первого прототипа добавляются инерция и привязка ближайшего элемента к центру.

## Открытые вопросы

1. Источник коллекции: только альбомы, которым поставлен лайк, или уникальные альбомы всех понравившихся треков?
2. Если у альбома несколько исполнителей, он должен находиться в каждой группе или только у основного исполнителя?
3. Должна ли карусель быть бесконечной и циклической?
4. Что происходит при нажатии на альбом: ничего, переход в Яндекс Музыку или открытие подробностей внутри приложения?
5. Приложение создаётся только для личного использования или планируется публикация?

## Рекомендуемая настройка Android Studio

- использовать стабильный канал обновлений Android Studio;
- использовать встроенный JDK Android Studio (`jbr` / Embedded JDK) для Gradle;
- в SDK Manager установить актуальную SDK Platform, Build-Tools, Platform-Tools, Command-line Tools и Android Emulator;
- создать основной AVD на профиле Pixel с актуальным стабильным Android и образом Google APIs;
- позднее добавить отдельный AVD с Android 8.0 / API 26 для проверки минимальной версии;
- оставить стандартное форматирование Kotlin и включить автоматическую оптимизацию импортов при сохранении;
- использовать Compose Preview для быстрой проверки компонентов и эмулятор для поведения всего приложения;
- не устанавливать сторонние плагины, пока в них не появится конкретная необходимость;
- по возможности перенести репозиторий в путь без кириллицы, например `C:\Projects\MyRecordCollection`, потому что Gradle-тесты некорректно работают в текущем пути профиля пользователя.

## Публикация APK через GitHub

Однократно создайте постоянный ключ подписи и сохраните его резервную копию. Потеря ключа не позволит устанавливать новые версии поверх уже установленного приложения.

```powershell
keytool -genkeypair -v -keystore release.jks -alias myrecordcollection -keyalg RSA -keysize 2048 -validity 10000
[Convert]::ToBase64String([IO.File]::ReadAllBytes((Resolve-Path .\release.jks))) | Set-Clipboard
```

В GitHub откройте `Settings → Secrets and variables → Actions` и создайте четыре repository secret:

- `RELEASE_KEYSTORE_BASE64` — содержимое буфера обмена после второй команды;
- `RELEASE_KEYSTORE_PASSWORD` — пароль хранилища;
- `RELEASE_KEY_ALIAS` — `myrecordcollection` или выбранный alias;
- `RELEASE_KEY_PASSWORD` — пароль ключа.

После настройки публикация выполняется командами:

```powershell
git tag v0.0.1
git push origin v0.0.1
```

Workflow `.github/workflows/release-apk.yml` проверит формат тега, запустит unit-тесты, соберёт подписанный APK и создаст GitHub Release с файлом `MyRecordCollection-v0.0.1.apk`.
